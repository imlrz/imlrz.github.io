Jev 的基本情况 · state in, decisions out

一个 state，多个共享该状态的 questions

  • state：字符串、object 或 array，是所有问题共享的语境。
  • questions：运行时声明问题、评分标准和合法候选。
  • answers：使用同名 ID 返回 typed value 与概率。
不是 JSON mode。 JSON mode 仍在自回归生成 token；Jev 声称直接并行产生类型化决策。
{
  "state": {
    "message": "I was charged twice. Fix this ASAP.",
    "duplicate_charge": true
  },
  "questions": {
    "intent": { "type": "choice", … },
    "frustration": { "type": "score", … },
    "needs_human": { "type": "noul", … }
  }
}

输入长度：当前公开 OpenAPI 没有披露硬性 context 上限；因此不把实测限制误写成架构上限。

Jev 的基本情况 · 3 primitives

三种输出，对应程序的三种控制结构

Choice · match / route

从运行时给定的候选中选一个；返回 choice、全部候选概率与 confidence。

Score · rank / threshold

对有序 rubric 评分；score 是各级别概率的加权期望，可为小数。

Noul · if

评估一个 yes/no 命题；单个数值就是 P(yes / true)，0.5 表示不确定。

结构化状态text / object / array
→
动态任务instructions + criteria
→
概率决策choice / score / noul
→
普通代码if / match / sort

所谓“不会 hallucinate”只能严格理解为：不会返回 schema 之外的值。它仍然可以在合法选项中选错。

Schema 语义 · intent 是什么

intent / frustration / needs_human 是调用者自定义的 question ID

  • 用来将请求里的问题和响应里的答案一一对应。
  • 真正定义任务的是 type、instructions 和 criteria。
  • criteria 的 key 是合法输出，value 是其语义描述。
key 可以是句子吗？ OpenAPI 把 choice name 定义为 string，因此技术上可以。但工程上建议用稳定短 key，把完整定义写在 value 中。
"intent": {
  "type": "choice",
  "instructions": "Which team should handle this?",
  "criteria": {
    "billing": "Payments, refunds, or charges",
    "technical": "Product malfunction",
    "other": "Everything else"
  }
}

// 响应使用同一个 ID
"intent": {
  "choice": "billing",
  "probabilities": {"billing": 0.96, …}
}
System One 的产品承诺 · 说法需分层

“并行”是同一请求的输出方式，不是 prefix cache hit

$0.042/ 1M input tokens · 官方定价
freeoutput tokens · 官方当前定价
70–500ms端到端 · 官方公布范围
255choice cardinality · 官方公布

官方确认的“并行”

一个 state 对应多个 questions，模型不用像 LLM 一样逐 token 解码长字符串；多个 typed outputs 在一次查询中返回。

不能据此推出 prefix hit

跨请求的相同前缀是否缓存、账单是否折扣，是 serving 层问题。当前没有官方证据支持“前缀命中”。

速度与价格来自 TypeSafe 自报；官方也明说 193.6× / 444.6× 是其 workflow 上偏高的增益，不应外推为所有任务的普遍结论。

RQ1 · 结论 · 强在哪里

证据支持的是“强 decision model”，不是“万能 LLM 替代者”

强证据

交换级 memory retrieval、规则分解后的 judge / scorer、保留概率的排序聚合。

中等证据

DRB2 接近前沿 LLM，DRB1 小样本接近 GPT-5.5；但仍需扩大同协议实验。

仍未证明

长上下文、复杂时序推理、视觉多模态、任意开放生成任务。

开源替代的当前排名：Nimble-9B 是最强的“不改架构”基线；Kev-4B 是更接近 dynamic decision readout 的架构实验。
RQ2

Jev 是如何出现的？

LLM 预训练带来通用表征；Jev 将输出空间从自由字符串改成动态决策，再用 RLCD 和数据把概率变得可用。

RQ2 · 必然性 · why now

Jev 的“现在出现”有四个必要条件

1 · 通用 LLM 表征

动态 label 的语义可以在运行时理解，而不是每个任务重新收集标注。

2 · 便宜合成数据

强 LLM 能够构造跨领域决策任务、反例、改写和软标签。

3 · 推理成本矛盾

生成式 frontier intelligence 很强，但高频、实时、机器消费的任务无法为长 CoT 付费。

4 · 产品界面改变

程序需要概率、类型和可组合控制流，不是更流畅的自然语言。

BERT 时代能不能出现？ 能出现“概率分类 API”，但很难出现同一个 zero-shot 模型在运行时理解新任务、新标签与复杂 state 的形态。
RQ2 · 架构 · backbone ≠ readout

最稳妥的抽象：pretrained LLM backbone + dynamic decision readout

预训练 LLMTransformer 通用表征
→
state + questions + options运行时任务语义
→
decision readout动态候选打分
→
RLCD正确性 + 校准

已公开

Transformer-based；从 pretrained base model 继续训练；new architecture、parallel sampler、RLCD。

合理推测

主干仍是 decoder-style LLM Transformer；改造集中在输入组织、mask、query / option 表征与 readout。

仍未知

是否使用原 LM head、是否有 scalar / pointer head、是否一次 forward，以及具体 attention mask。

不要把“Decoder-only / encoder / parallel queries”并列为三种底层架构。LLM Transformer 是 backbone；其上的动态读出才是未知变量。
RQ2 · 架构 · 为什么不是固定分类头

运行时候选会变，所以不可能只是 Linear(h, fixed_num_classes)

zᵢ = F(state, question, optionᵢ)
pᵢ = softmax(z)ᵢ

同一个共享 F 对任意数量、任意语义的候选打分，才能支持 zero-shot dynamic label space。

1 · 受限 token logits

把 options 映射到专用 token，只读决策位置的 logits，不继续文本 decode。

2 · hidden state + shared scalar

每个 option 先得到表示，再用共享 head 读出 zᵢ。

3 · parallel decision queries

专用 question / option query 共享 state，在一个并行 sampler 中读出多个 scalar。

三者是同一 LLM backbone 上的读出设计，可以混合；官方尚未披露 Jev 采用哪一种。

RQ2 · 训练方法 · RLCD vs RLHF / RLVR
路线优化目标奖励 / 监督输出
RLHF人类偏好的回答human preference / preference model有帮助、自然的文本
RLVR可程序验证的最终结果checker / unit test / rulereasoning + answer
RLCD决策正确且概率诚实programmatic outcome / target distribution?typed probabilities

RLCD 现在更像一个 task / North Star，不是已公开的唯一优化器；截至 2026-09-23 没有技术报告或完整损失函数。

RQ2 · 数据 · data matter

真正困难的不是生成很多文本，而是构造可信的概率目标

  • 已公开 TypeSafe 称自己为 data research lab；训练数据由团队制作，不用客户数据训练。
  • 仍未知 规模、生成模型、过滤流程、软标签来源、领域配比。
  • 合理推测 同义改写、选项乱序、否定/反事实、OOD 和带已知 posterior 的合成环境都很关键。
hard label 不够。 标签为 A 无法告诉模型这是 51/49 的模糊样本，还是 99/1 的确定样本。
RQ2 · Base model · evidence ladder

当前可讲的结论是“像 Qwen3.5”，不是“已证实为 Qwen3.5”

1 · 官方证据

Jev 从 pretrained base model 出发，是 transformer-based model。官方未给出模型名、参数量或 tokenizer。

2 · 社区线索

小红书截图/社区讨论将特征指向 Qwen3.5；Nimble 和 Kev 也都选择 Qwen3.5 来复制这种形态。

3 · 不能排除

自研 dense / hybrid backbone、其他开源基座、或混合多个技术路线；性能轮廓不能唯一反推 base。

组会表述建议：“Qwen3.5 是当前有支持的社区假设，但官方尚未确认。”

RQ3

Jev 是否有开源复现？

没有项目复现了 proprietary Jev / RLCD。但 Nimble 和 Kev 分别验证了“原 LM head”与“新 decision head”两条路。

RQ3 · Nimble-9B · 最小改造路线

保留 Qwen3.5-9B 的生成架构，只训一个 token 的 A/B/C 候选 logits

Base model

Qwen/Qwen3.5-9B 作为直接父模型；它本身已是 post-trained checkpoint，底层来自 Qwen3.5-9B-Base。

Data

2,676 train + 324 eval；1,338 对 contrastive pairs，34 task families / 10 categories。数据与构造代码已开源。

Architecture

不加新 head；使用原 vocabulary LM head，对单 token 候选 A/B/C 做 restricted logits 交叉熵。

Training

LoRA r=16 / α=32 / dropout .05，1 epoch，lr 5e-5，effective batch 8，BF16 H100。SFT / CE，不是 RL。

意义：它验证了“不需要新底层架构，只改训练任务也能做出强 typed decision model”；但单 token 候选限制了表达形态。

GitHub · bespokelabsai/nimble ↗ · Hugging Face ↗

RQ3 · Kev-4B · 专用 decision readout

Qwen3.5-4B-Base + LoRA + pointer head，让每个 option 成为动态可打分对象

Base model

当前 main 为 Qwen/Qwen3.5-4B-Base；旧 qwen3 tag 才是 Qwen3-4B-Base。

Data

10 个公开源×1,000 + 896 policy + 1,680 compositional = 12,576；数据开源为 kev-suites。

Architecture

每个问题独立成 causal row 并共享 state prefix；使用 decide hidden state 与 option-end hidden state 的 pointer score。

Training

LoRA r=16，初始 2 epochs / lr 5e-5；delta 1 epoch / lr 2e-5；监督 CE，无 RL；事后温度 T=2.14。

scoreᵢ = q(hdecide) · k(hoption-end,i) / √256
p = softmax(score)

TypeSafe 的理念：重新选择任务

Discussion 2 · System One & System Two

System One 是任务形状，不是已公开的神经网络类型

System One

快速、高频、输出空间已知的决策；目标是软件直接消费。

System Two

慢速、审议、长链推理、规划与自由生成；更像 reasoning LLM / agent。

Jev 之名来自 Jevons paradox：单位智能越便宜，可能解锁更多原本不值得自动化的决策，反而增加总需求。

Discussion 2 · The Bitterest Lesson

官方的优先级排序：right task > data > compute > algorithms

Right task机器真正需要什么输出？
→
Data能否覆盖现实决策分布？
→
Compute还能扩大多少？
→
Algorithms最后才是巧妙方法
Jev 的核心叙事：预训练已经产生大量通用智能；与其让它生成人类喜欢的长文字串，不如换成软件可以依赖的决策任务和概率界面。

这也解释了为什么 RLCD 现阶段首先是任务定义，其次才是具体算法。

Discussion 2 · Lies, Damned Lies, and Benchmarks

一个 benchmark 即使没有训练集泄漏，也可能被“间接过拟合”

模型追 benchmark

训相似数据，或试足够多超参数，然后选中公开分数最高的 checkpoint。

benchmark 追模型

新模型与直觉冲突时，人们修订指标，直到排名看起来“合理”。

用户责任

运行私有 eval；报告 caveat、负例和试验次数；把每次结果当成时间快照。

对我们这组实验的启示：MAB 60、InMind same20、DRB1 same17 都不能单独支撑普遍性结论；更重要的是找到它在什么粒度、读出和聚合规则下失效。

Discussion 1 · 1 / 3

泛化性

与固定任务的 BERT classifier 相比，Jev 的底座有更广的通用知识；给它新的问题和候选，它也能直接做判断。

MAB · 同一 60 题

Top-5 检索后回答正确：Jev 45/60（75.0%）；Laya 19/60（31.7%）。

InMind · 同一 20 题

Exchange gold chunk 检索：Jev R@1 85%、R@5 90%；Laya R@1 10%、R@5 15%。

怎么理解：同样拿来判断一段 memory 对问题有没有用，Jev 在这两组任务上明显更强。但 Jev 与 Laya 的底座、训练和长文本处理都不同，不能只凭这两个分数证明优势全来自“世界知识”。

来源：本地交叉测试报告 ↗。MAB 是固定 60 题子集；InMind 的 exchange 粒度比 session 粒度更适合直接比较。

Application · 从 API 到方法

最直接的三类应用

Judge / Scorer

代码、报告、agent trace、安全规则、风险和质量维度的并行评分。

Classify / Label

路由、意图、优先级、实体和政策标签；标签集可运行时更新。

Jev post-train

先用通用 Jev 冷启动，累积 outcome / 私有数据后，再蒸馏成更小的专用 decision model。

现实闭环：Jev 处理新任务和 OOD；成熟的固定高流量任务逐步蒸馏到本地小模型。这不是“淘汰分类器”，而是改变分类器的创建方式。
Open problems · 下一步不只是变大

把 System One 扩展到更复杂任务，需要打破当前的简化假设

1 · Reasoning Jev

能否在不回到长链自回归生成的前提下，引入更稳定、更便宜的内部计算？

2 · Long-context Jev

如何在长状态中保留检索召回与校准？是换 base，还是引入 hierarchical readout？

3 · Multimodal Jev

当前 Doom demo 读取的是带文本的结构化状态，不是图像。真多模态需要 vision / audio encoder 或多模态 base。

Takeaways · 三句话

如果只记住三件事

01 · 界面

Jev 的关键不是“小 LLM”，而是从自由文本改为动态 typed probabilities。

02 · 证据

它在 retrieval / judge / scorer 上已显示前沿能力，但长上下文、推理和多模态尚未证明。

03 · 护城河

架构可能只是一部分；更难复制的很可能是任务定义、合成数据、校准与 serving 联合优化。
